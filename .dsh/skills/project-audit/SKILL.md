# 开场勘察协议

用户每次开工都以一次状态勘察开始。**这个协议的唯一目的是：用最少的 token 恢复到可信的当前状态，然后给出可执行的下一步。**

## 铁律

1. **先读快照，再读代码。** 禁止一上来就全库通读。
2. **没有 `文件:行号` 的断言不算结论。** 不许写「应该没问题」「看起来正常」。
3. **设计口径不可违反。** 与 `planning/design-rulings.md` 冲突的代码是 bug，不是「另一种实现」。
4. **区分「我能做」和「我不能定」。** 机制语义、数值口径、美术取舍 → 必须回抛给用户。

## 流程

### 第 0 步 — 读三个真相文件（按序）

| 文件 | 作用 |
|---|---|
| `planning/STATE.md` | 当前状态快照（唯一事实来源） |
| `planning/design-rulings.md` | 用户拍板过的设计口径，**必须遵守** |
| `planning/main-loop-repair-plan.md` | 历史修复日志（只看最近一节，不要通读） |

### 第 1 步 — 校验快照是否仍然为真

只做**廉价核验**，不要重读全库：

```powershell
git rev-list --count HEAD                                  # 提交总数
git rev-list --left-right --count origin/main...main       # 领先/落后
git status --porcelain                                     # 工作区是否干净
python -c "import json;print(len(json.load(open('resources/block_defs.json',encoding='utf-8'))['blocks']))"
python -c "import json;print(len(json.load(open('resources/enemy_defs.json',encoding='utf-8'))['enemies']))"
```

抓取数量级变化（Block 数、敌人、脚本数、美术资源）。**发现快照与代码不符时，当场修正 `STATE.md` 并在报告中说明改了什么。**

### 第 2 步 — 找真问题，不是找漂亮话

按优先级找**会破坏一局体验**的东西，参照顺序：

- 软锁 / 卡死 / 无法通关
- 可无限刷的奖励、经济、计数（防刷）
- 跨战斗或跨存档的状态泄漏（占格、临时 Stat、缓存）
- 机制方向反了（读错的一侧、算错的时机）
- 死代码、悬空引用、被删掉仍在调用的东西

每条必须给出：**现象 → 后果 → 触发路径 → `文件:行号`**。

### 第 3 步 — 按固定格式输出

用户习惯的结构，不要自创格式：

```markdown
# 项目状态评估

**结论：<一句话，说清现在能不能玩、卡在哪>**

- 内容量：<N Block / N 敌人 / N Behavior>
- 工程：<工作区是否干净、领先 origin 多少、测试状况>
- 文档：<STATE.md 是否可信，哪些文档滞后>

## 必须解决的问题

**P0 — <类别>**
1. **<问题名>**：<现象与后果>（`路径:行号`）
   - 触发：<复现路径>
   - 方案：<一句话>

**P1 — <类别>**
7. ……

## 建议的下一步方向

1. ……（按投入产出排序）

## 待裁决

| # | 问题 | 选项 | 我的建议 |
|---|---|---|---|
| 1 | …… | A / B | A，因为…… |
```

### 第 4 步 — 分类处理，不要一律发问

把上面每一件事塞进两类之一：

- **可直接执行** —— 纯实现、纯验证、纯清理、纯文档同步。**不要问，直接做。**
- **需你拍板** —— 机制语义、数值口径、美术风格、破坏性操作。**汇总进「待裁决」表，让用户一行回复即可作答。**

> 用户明确讨厌「需要我继续吗」。只有当某件事真的只有他能决定时才停下。

## 输出后

如果用户批准了「可直接执行」的那批，**接着干，别等**。干完走 `session-handoff`。
